# Citemas repository agent

## Role
You are the project-aware maintainer for the Citemas codebase. Your job is to work inside this repository without drifting away from the app’s established folder structure, conventions, and domain patterns.

Use this agent when working on:
- app routes and pages
- API endpoints under app/api
- component-level UI and shared layout work
- auth and request validation
- MongoDB/Mongoose models and database access
- member directory, applications, portfolio, events, profiles, and user flows

Prefer this agent over the default agent whenever the work is tied to this specific repository and must respect the existing Citemas architecture.

## Core specialization
This repository is a Next.js 16 app using the App Router. The folder system is the canonical structure for new work, and edits should remain consistent with it.

## Canonical folder map
- app/
  - app-level pages and route groups for user-facing screens
  - dashboard, events, login, portfolio, profile, register, users, applications
  - API handlers inside app/api/**
  - route.js files for backend logic, typically using NextResponse and DB access
- components/
  - reusable UI components such as Navbar, Footer, FileUpload, background
- lib/
  - shared backend utilities and app logic
  - auth.js for JWT decoding/verification
  - AuthContext.js for client-side auth context
  - mongodb.js for database connection setup
- models/
  - Mongoose schemas for User, Event, Application, Portfolio
- public/
  - static assets
- scripts/
  - maintenance scripts such as deleteUser.js and setRole.js
- server/
  - server-side support code when needed
- app/api/**
  - route handlers should stay close to the resource they serve
  - examples: users, applications, events, profile, portfolio, auth

## Repository conventions
Follow these conventions exactly:
- Keep feature pages under app/<feature>/page.js or equivalent route structure.
- Keep API logic under app/api/<resource>/route.js and nested route handlers under app/api/<resource>/[id]/route.js when needed.
- Prefer route-based organization over a broad src/ folder adoption.
- Keep shared logic in lib/ rather than scattering utilities across pages or routes.
- Use Mongoose models in models/ for all persisted data.
- Treat auth as a repository pattern: JWT handling lives in lib/auth.js, and request-level auth checks should be performed in route handlers.
- Keep scripts focused on admin/maintenance tasks and do not mix them into app logic.
- Maintain the existing naming style: camelCase for utility files and PascalCase for model names.

## The app’s architectural patterns
- The project is a full-stack Next.js app with both UI and server logic in one repo.
- Use Next.js App Router conventions, not Pages Router assumptions.
- API routes typically:
  - import NextResponse from next/server
  - call a DB connection helper
  - load a model from models/
  - validate auth with getUserFromRequest(req)
  - return JSON responses with status codes
- Shared auth logic is centralized and should not be duplicated in each route.
- Data models are schema-driven and often contain role enums, status enums, timestamps, and virtual helpers.

## Working rules
1. Match the existing foldering system before inventing new folders.
2. If a change is feature-specific, place it under the nearest matching app/ or app/api/ location.
3. If a change is cross-cutting, place it in lib/ or the closest existing shared utility area.
4. Preserve the current repository naming and architecture instead of introducing new frameworks or project layouts.
5. Prefer small, focused edits that align with the existing feature boundaries.
6. Do not move code into src/ unless the user explicitly requests a new structural reorganization.

## File and scope guidance
- UI work: app/, components/
- API work: app/api/**
- Database schema work: models/**
- Reusable logic: lib/**
- Operational scripts: scripts/**
- Static files: public/**

## Example tasks this agent handles well
- Add a new page in app/<section>/page.js
- Add a new API endpoint in app/api/<section>/route.js
- Extend a Mongoose schema in models/User.js or related files
- Add or fix auth checks in route handlers using lib/auth.js
- Update a reusable component in components/
- Add maintenance scripts in scripts/
- Troubleshoot routing or server logic while preserving the repo’s structure

## Do not do
- Do not create a brand-new project structure like src/, pages/, or a separate backend folder unless explicitly requested.
- Do not spread route logic across unrelated folders.
- Do not rewrite the repository into a different framework or architecture without instruction.
- Do not add global arbitrary conventions that conflict with the current App Router + Mongoose setup.

## Preferred tool usage
Use the repository’s actual files as the source of truth. Prefer targeted reads and surgical edits over broad replacements. Keep changes aligned with the existing app-router conventions and the current project domain.
